- [x] FR-144 DEFECT (TOOLING, found by T-EPOCH4's freeze 2026-08-28; FIXED
  2026-08-28): THE IMPROVEMENT HARNESS'S FROZEN-CORPUS PREMISE WAS BROKEN in
  both of its consumers, and nothing detected either. The epoch mechanism
  exists so a clippy delta between two emitter revisions is attributable to the
  emitter ALONE -- a paired comparison over a pinned population.
  (1) EPOCHS 1, 2 AND 3 HAD ALL DRIFTED. `verify` returns 1 for each (epoch-1
      3 CONTENT-CHANGED files, epochs 2/3 two each). PRE-EXISTING, confirmed by
      running the PRE-PATCH `epoch.py` from `git show HEAD:` against the same
      tree: identical output. So every trajectory recorded against epochs 1-3
      was measured over a population that had already moved. Nothing noticed
      because `ledger_append` compared the epoch DOCUMENT's stored hash against
      the ledger's, never against the files on disk.
  (2) THE COMMITTED RATCHET WAS MEASURING ACROSS A CHANGED POPULATION: it fired
      at HEAD (`68 -> 72`) while its baseline recorded 180 `.c` files against a
      corpus of 186, so the +4 was attributable to nothing. Not in the lit
      gate, which is why it went unnoticed.
  FIXED, all three directions, which turned out to be complementary:
    (a) DRIFT GUARD. A drifted or unpinned population is now a LOUD refusal
        BEFORE any measurement, not a silent wrong number. Demonstrated by
        editing a pinned file: `PIN CHECK FAILED ... epoch-4 DRIFTED (1 files
        no longer match the freeze) ... Refusing: a delta measured over a moved
        population is attributable to nothing.` `ledger_append` now goes
        through the same check.
    (b) RATCHET RE-BASED onto epoch 4, so the DEFAULT invocation is a paired
        comparison over a pinned file list: `238 -> 238 (+0)`, exit 0, 0
        skipped. `--baseline`/`--file-list` overrides still work, and an
        EXPLICIT `--file-list` deliberately never ratchets ("measurement only")
        so a future epoch-5 slice run is not coupled to epoch-4's state.
    (c) EPOCHS 1-3 CLOSED AS HISTORY, deliberately NOT re-frozen -- re-freezing
        would make `verify` pass and DESTROY the evidence. `verify --id 1|2|3`
        still exits 1, now printing the closure alongside the drift, and
        `ledger-show` prints a closure banner above the descent so 798->350 can
        never be read as current evidence. Closure lives in a fresh
        `epoch-status.json` (immutable-by-default; `epoch-N.json` and
        `ledger.json` bytes untouched) recording `closed_at`, the rev, and each
        drifted file WITH GIT BLAME: epoch-1 `link-merge-e2e.c` [e91c45c],
        `planner-rejection-builds.c` [d6ef2ad], `preserve-c-names.c` [0afcbac];
        epochs 2/3 `planner-rejection-builds.c` [d6ef2ad], `range-for.c`
        [a308e45].
  THE MEASUREMENT REPRODUCED EXACTLY, which was the check worth demanding
  rather than assuming: epoch-4's baseline was taken at 556677d and re-measured
  at 4d29a39 (which touched only `nix/`), giving the same 238 linted / 0

  THE RATCHET STILL FIRES, demonstrated rather than asserted: hand-lowering the

  controller's `--update`/`git add` now name the SAME path, so it can no longer
  commit a file the ratchet does not read. A gated test fails if they ever
  diverge again.
