- [x] W2.20 `std::map`/`std::set` -> `BTreeMap`/`BTreeSet`. Spike
  verdict **GO-WITH-CONSTRAINTS** (2026-08-21). BTree, not Hash:
  `std::map`/`std::set` are ORDERED and their iteration order is
  observable in stdout, so the byte-diff oracle forces the ordered Rust
  container -- and `std::unordered_map`/`unordered_set` are therefore
  REJECTED, with the reason in the wording itself: their order is
  unspecified and no Rust container reproduces it byte for byte.
  Admitting them would be a silent nondeterminism channel.
  THE `operator[]` TRAP TURNED OUT TO HAVE THREE HEADS, and only the
  first was the one this entry predicted:
  (a) **READ-POSITION MUTATION.** `int miss = m[99];` INSERTS, and
  `m.size()` observes it; Rust's `Index` would panic instead. All four
  spellings (read, write, `+=`, `++`) lower to
  `*Entry::or_default(BTreeMap::entry(&mut m, k))` and byte-diff clean.
  (b) **E0499, not anticipated.** Two live map places in ONE statement
  is a hard borrowck error -- `m[1] = m[2]` creates two `&mut m`
  borrows. Multiple READS are fine (the importer emits place-then-load
  back to back and NLL kills the first borrow), so the failing case is
  specifically assignment, because `emitAssignToPlace` emitted the LHS
  place FIRST.
  (c) **AND LHS-FIRST IS ITSELF A C++17 MISCOMPILE**, which is why the
  fix for (b) was mandatory rather than a workaround. P0145R3 sequences
  E2 BEFORE E1 in `E1 = E2` and `E1 op= E2`. Measured with an
  observable side effect on both clang++ 21.1.8 and g++ 15:
  `std::map<int,int> a; a[1] = (int)a.size();` prints `a1=0 asize=1` --
  the size is read BEFORE the default-insert, where LHS-place-first
  would print `a1=1`. The assignment path now evaluates the RHS to a
  value first, which simultaneously fixes the borrowck error and the
  sequencing, and is byte-identical to native for `m[1]=m[2]`,
  `m[1]+=m[3]` and the nested `m[m[1]]=7`.
  A SECOND SILENT-MISCOMPILE TRAP THE BRIEF DID NOT LIST: **C++
  `map::insert` does NOT overwrite an existing key; Rust's
  `BTreeMap::insert` DOES.** Measured: after `m[1]=10`,
  `m.insert({1,99})` leaves `m1=10` and returns `.second=0`. The naive
  name-to-name mapping is wrong code, so `insert`/`emplace` are LOCATED
  rejections this wave, with the correct lowering (`entry(k).or_insert`)
  named in the wording. `std::set::insert` IS admitted -- measured
  exact: neither language's version replaces, and both return the same
  bool.
  ITERATION had a real structural blocker with a zero-new-op answer.
  `emitCXXForRangeStmt` is an INDEX desugar (`emitrust.subscript` +
  `len()`), and there is no iterator-loop op in the dialect
  (`emitrust.for` is range-only, `emitrust.verbatim` has no region,
  `emitrust.match` is data_enum-only), so a BTreeMap cannot ride it.
  The shipped shape is an ORDERED KEY SNAPSHOT feeding the existing
  index loop: `Vec::from_iter(Iterator::cloned(BTreeMap::keys(&m)))`,
  then the ordinary i64 index loop indexing the map by each key. Every
  intermediate iterator type is NAMEABLE, which matters because
  `emitLetPrologue` requires a type annotation. The same UFCS free-call
  form is what makes the entry API expressible at all:
  `emitrust.method_call` renders `place.method(args)` with no chain
  suffix and requires an LValue receiver, so `m.entry(k).or_default()`
  is NOT expressible -- but `Entry::or_default(BTreeMap::entry(&mut m,
  k))` is two plain `call_opaque`s feeding a `deref`, which renders and
  borrow-checks.
  ADMITTED: `size`/`empty`/`clear`/`count`/`erase(key)`/`at`, the
  `m.find(k) != m.end()` IDIOM (matched structurally as a whole, before
  operand type mapping, since the iterator type would otherwise reject
  first), `set::insert`, and `for (auto [k,v] : m)` / `for (int x : s)`.
  `at()` on a missing key throws in C++ and panics in Rust -- the same
  safe-refinement argument W2.6 used for vector `front`/`back`, and the
  corpus oracle requires exit 0 so no passing entry can observe the
  divergence.
  KEY AND VALUE TYPES are screened, not assumed: integer/bool/char keys
  only. `double` keys reject (not `Ord` in Rust), `std::string` keys
  reject, struct keys reject, and a comparator other than `std::less`
  rejects. Value types were narrowed BELOW this entry's original
  proposal -- `std::string` values reject too, because a String value's
  store and load through the entry place raises an untested move/clone
  question and a narrow byte-diff-clean subset beats a wide guess.
