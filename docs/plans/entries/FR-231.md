- [x] FR-231 (opened and LANDED 2026-09-10 from an owner question -- "does it
  make sense to transform C++ namespace to Rust mod?"): **YES, AND FR-159 HAD
  ALREADY BUILT 80% OF IT -- BUT THE SYMBOL IS CONSUMED AS AN IDENTIFIER IN
  SIX MORE PLACES THAN THE NAMING LAYER, AND EVERY ONE ABORTED OR EMITTED
  NON-RUST.**
  **WORTH +0 TRACTOR BY CONSTRUCTION** -- the corpus is C, C has no
  namespaces, and the flag is OFF by default. This is a readability/product
  item and is filed as one; nothing here is yield. Measured 57/252 before and
  after.
  **WHY IT WAS TRACTABLE AT ALL.** Namespaces were FLATTENED into a name
  prefix by `namespacePrefix()` -- `geo::inner::twice` became
  `ns_geo_ns_inner_twice`, degrading with depth. But FR-159's per-TU module
  emission keys purely on the SYMBOL SHAPE: any top-level item named
  `crate::<module>::<leaf>` is bucketed and rendered inside `mod <module>`,
  and its own comment says "use sites already spell the whole path, so nothing
  else in the emitter changes". So the core of the feature is one function
  returning `crate::geo::inner::` instead of `ns_geo_ns_inner_`.
  **NAMESPACE REOPENING COMES FREE** -- bucketing is by path string, so a
  namespace split across a header and an impl lands in one `mod`. Pinned, not
  built.
  **THE FLAG** mirrors FR-53's `idiomaticRenameEnabled()` exactly, for its
  exact reason: the same naming primitives feed the importer, the FR-40 item
  graph and the clang-free emitter, and they must agree byte for byte.
  `namespaceModulesEnabled()` lives beside it in the clang-free
  `RustCasing.h`; `--namespace-modules`; **default OFF**.
  **MY SPEC WAS WRONG OR INCOMPLETE IN THREE PLACES, and the third was the
  bulk of the work:**
   1. **"`ImplOp` has no module form" -- WRONG in effect.** `ImplOp` has no
      `sym_name`, so it is never bucketed and never reaches that refusal at
      all: it renders `impl crate::geo::Vec { .. }` at the crate root, which
      rustc accepts. **Gap 2 was free.**
   2. **Nesting needed more than a tree.** A plain `mod inner` at depth > 1 is
      **E0603** from the root, so it must be `pub(crate) mod`; and `use
      super::*` is wrong there because `super` is the parent NAMESPACE module,
      so it must be `use crate::*`. Depth 0 keeps the bare `mod` and no import,
      which is what reproduces FR-159's bytes exactly.
   3. **"EXACTLY THREE CALL SITES" -- WRONG, and expensively.** There are
      three *namespace-prefix* sites, but the symbol is consumed **as an
      identifier** at six more, and every one aborted or emitted non-Rust on
      legal C++ under the flag: the `emitrust.variable` verifier
      (`variable name must be a non-empty Rust identifier, but got
      "crate::geo::counter"`), the FR-62 actor owner struct named
      `Crate::ns::tu0SeedActor` (a `toUpperCamelCase` run over a PATH), its
      `varName` and field names, and -- worst -- an arm call site emitting
      **`self.crate::ns::pick(1i32)`**, passing the whole symbol as a method
      name while `emitFunc` printed the leaf. That last one is **exit-0
      unbuildable**. Fixed with one `flattenItemPath` at the
      identifier-manufacturing sites plus a leaf take at the `MethodCallOp`,
      with a collision guard so a flattened binding landing on an existing
      crate-root symbol keeps its module form instead of shadowing that static
      -- gated on the symbol containing `::`, so no flagless compile reaches
      it.
  **THE EXPORT COUPLING IS REFUSED, NOT PAPERED OVER.** FR-159's emitter skips
  any module-path item in the C-ABI export loop because such items are
  TU-local; under this flag that implication no longer holds, so the driver
  refuses the combination at option-validation time:
      error: --c-abi-exports does not apply under --namespace-modules: an item
      inside a Rust module is not exported, so a namespaced function would
      silently lose its C symbol
  The NON-refused consequence is pinned positively rather than left implicit:
  a `--crate-type=lib` namespaced item is `pub(crate)`, so a library whose API
  lives in a namespace has **no public surface** under the flag.
  **THE `tuTag` COMPOSITION WAS BACKWARDS** and is fixed by moving the tag to
  the LEAF -- `crate::ns::tu0_helper`, not `tu0_crate::ns::helper`. The
  `toScreamingSnakeCase` fold for globals had to be confined to the leaf for
  the same reason (over the whole string it spells `CRATE::GEO::X`). An
  ANONYMOUS namespace becomes `mod anon`, deliberately: Rust has no anonymous
  module, and it is the `tu<N>_` leaf tag that actually separates two TUs'
  anonymous namespaces.
  `#[allow(non_snake_case)]` on an emitted `mod` is **load-bearing**, proven
  by deleting it: `module 'a__b' should have a snake case name`. A doubled
  underscore survives `toSnakeCase`, so it fires in the DEFAULT rename mode,
  where there is no crate-level blanket allow.
  **A PRE-EXISTING COLLISION HAZARD FOUND AND DELIBERATELY NOT FIXED:** an
  `enum` inside a namespace takes **no namespace prefix at all** --
  `namespace lib { enum Color ... }` emits a root-level `Color` in BOTH flag
  modes. That is an existing defect in where `namespacePrefix` is applied,
  identical with and without this change, and it should get its own entry
  rather than being folded into a flag commit.
  Gate 1066/1066 (1061 + 5 new tests). **Golden movement with the flag OFF:
  1338 files, 963 identical, 375 rejected by both, MOVED = 0** -- which is the
  entire point of gating it. With the flag ON, an additive sweep of all 79
  `test/EndToEnd/*.cpp` found 77 byte-identical and zero flag-caused
  mismatches. Clippy 57 (+0) at epoch-7, binding both axes flat, CTestSuite
  220/220, Cpp17Suite 35/35 with manifests untouched, TRACTOR 57/252 unmoved.
  All re-verified independently in the main tree.
  NOT DONE, and worth knowing before anyone extends this: use sites inside a
  module still spell the ABSOLUTE path (`fn norm(p: &crate::geo::Point)`
  inside `mod geo`), which is correct and compiles but is not maximally
  idiomatic. FR-159's comment explains why -- a module-relative path is E0433
  in an fn-ptr table payload -- so shortening it needs a position-aware rule,
  not a blanket change.
