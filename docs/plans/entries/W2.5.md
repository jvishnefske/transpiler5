- [x] W2.5 C++17 `if`/`switch` init-statements and the condition-declaration
  form (task-002 of the W2.4 loop). The located rejections in `emitIfStmt`
  ("declaration in if condition") and `emitSwitchStmt` ("declaration in
  switch condition") are replaced by a hoisting desugar: the init-statement
  (`IfStmt::getInit()`/`SwitchStmt::getInit()`) and/or the condition
  declaration (`getConditionVariableDeclStmt()`) emit as ordinary
  statements into the enclosing block, in source order, before the
  condition is evaluated. Soundness argument recorded at the code site:
  both slots are evaluated exactly once in C++, so hoisting is exact; the
  variable outliving the statement's C++ scope is unobservable without
  destructors (outside the subset); and a later same-named variable is a
  DISTINCT VarDecl (locals are keyed by decl identity), which the Rust
  emitter uniquifies (`r`/`r_1`/`r_2` in the spike's emitted crate) — no
  reliance on Rust `let` shadowing. Both getters are always null for C
  input, so the C path is untouched by construction. `emitIfStmt`'s
  constant-condition dead-arm elision composes correctly: the hoisted
  init's side effects are already emitted before the elision check runs.
  Spike verdict GO: a torture program with two same-named init variables
  in one block, an `if` with BOTH slots populated (`if (int base = v - 3;
  int r = f(base))`), and a switch-with-init byte-diffed clean against
  clang++ (`84 22 -1 -7`). `while`/`for` condition declarations stay
  rejected (a `while` condition declaration re-evaluates per iteration —
  hoisting would miscompile; untouched this wave).
