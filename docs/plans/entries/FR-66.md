- [x] FR-66 macOS/Darwin host port (VALIDATED 2026-08-10: meson test 552/552
  on arm64 Darwin). The full suite (build + lit) runs green on
  a Darwin host with the same oracles as Linux — no byte-diff or byte-identity
  oracle weakened without a `system-darwin`-gated, comment-documented reason.
  Acceptance: (a) `meson test -C build` 100% on Darwin; (b) the EndToEnd
  byte-diff tests compare against clang-built natives exactly as on Linux;
  (c) platform differences are expressed as lit substitutions/features, not
  relaxed CHECK lines. Three mechanism classes found and fixed:
  **1. SDK/sysroot discovery.** ClangTool never runs the driver's Darwin SDK
  detection, and lit sandboxes the environment, so hosted-header imports
  (`stdio.h` etc.) failed to find headers. Fix: configure-time probes bake
  `EMITRUST_CLANG_SYSROOT` (`$SDKROOT` / `xcrun --show-sdk-path`) and
  `EMITRUST_CLANG_LIBCXX_DIR` (asked from the nix clang wrapper via `-v`)
  into the import library (both CMake and meson, per the dual-build rule);
  `ClangProjectParser` appends `darwinSysrootArg()`/`darwinLibcxxArg()` to
  both `buildCommandLine` and `filterRecordedCommandLine`, with run-time
  overrides `EMITRUST_SYSROOT`/`EMITRUST_LIBCXX_DIR`.
  **2. Payload section naming.** ELF `.emitrust` is not a valid Mach-O
  section spelling; `emitRustSectionSpec()` emits `__TEXT,__emitrust` on
  Mach-O and `LinkMerge` matches the bare `__emitrust` segment-local name on
  the read side. Tests use a `%emitrust_section_spec` lit substitution.
  **3. Tool-format differences.** llvm-objcopy `--remove-section` on Mach-O
  leaves an empty segment load command behind, so the shim byte-identity
  `cmp` (strip-payload == plain-clang object) cannot hold on Mach-O; that
  single check is gated ELF/COFF-only with the reason documented in the test
  (`test/Driver/emitrust-clang-shim.c`) — the functional checks still run.
  Validation on the full suite surfaced six more classes, all fixed as real
  code (no oracle weakened):
  **4. Fortify rewrites.** The Darwin SDK defaults `_USE_FORTIFY_LEVEL` to 2,
  macro-rewriting `strcpy`/`sprintf`/... into `__builtin___*_chk` builtins
  the importer does not model; the importer's own command lines append
  `-D_FORTIFY_SOURCE=0` on Darwin (behavior-identical for well-defined
  programs, so the byte-diff against the fortified native build holds).
  **5. rustc SDK discovery.** cargo's native link resolves the SDK from
  `$SDKROOT` (falling back to `xcrun`, which fails in the sandboxed lit
  env); lit.cfg.py forwards the dev shell's `SDKROOT` on Darwin.
  **6. `%#g` carry quirk is glibc-only.** The emitted float shim's
  rounding-carry fraction-drop (`1.e+06` where Darwin's libc prints
  `1.00000e+06`) is now gated on `cfg!(target_os = "linux")` — the oracle is
  parity with the HOST libc the native reference links.
  **7. `__sFILE` carries function-pointer fields.** glibc's `_IO_FILE` has
  only data-pointer members (inert i64 slots), but Darwin's `__sFILE` has
  cookie-I/O callbacks whose `void *` params reject in fn-ptr signature
  mapping, making every FILE* signature un-importable; a function-pointer
  field of a SYSTEM-HEADER record now stores as the same inert i64.
  **8. `va_list` is canonically `char *` on AArch64 Darwin.** The C99-37
  canonical-type checks either missed it (locals/params imported as plain
  pointers) or would swallow every `char *` (the va-clone local skip); a new
  sugar-chain detector (`isVaListSugarType`) keys the rejection and the
  clone skip on the `__builtin_va_list` typedef instead. Also fixes the
  latent clone-local bug on Darwin.
  **9. `long` maps by target width.** `mapType`/`mapSpeculativeScalarType`
  hardcoded Long/ULong to 64 bits; a forwarded `-m32` triple makes long 4
  bytes, and 32-bit Darwin triples spell `size_t` as `unsigned long` (Linux
  i386 says `unsigned int`, which is why the hardcoding survived there), so
  Long/ULong now map via `ASTContext::getTypeSize` — 64-bit targets
  unchanged, and the FR-56 target-abi golden now holds on both hosts.
  Darwin's `stdin`/`stdout`/`stderr` macro spellings (`__stdinp`/...) are
  canonicalized by `canonicalStreamName` at the fprintf-devirt checks and
  in pointer diagnostics, so recognition and messages use the ISO names.
