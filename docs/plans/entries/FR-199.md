- [x] FR-199 (opened and LANDED 2026-09-05; FR-193 items 16-17): **STATEMENTS
  ON A LOOP-EXIT PATH RAN AFTER THE LOOP-BODY LOCAL'S DESTRUCTOR. REFUSED,
  NOT FIXED -- AND THE REFUSAL IS THE RIGHT CALL.**
  **THE NAMED LEAD WAS WRONG.** The spec pointed at
  `HoistEscapingLoopPlacesPass`; that pass already refuses droppy places. The
  cause is one level up, in MLIR's `lift-cf-to-scf`: a block that is
  LEXICALLY inside the loop body but from which EVERY path leaves the loop is
  not on the cycle, so the structurizer places it AFTER the loop and
  dispatches it on an exit index. The emitted `let` for a loop-body local
  drops at the end of the loop-body REGION, so the relocated effect lands
  after the drop. **In C this is unobservable; a destructor makes it a silent
  reorder.**
  **WHY REJECTION RATHER THAN A FIX, and this is the load-bearing judgement:**
  making the shape correct needs a break/return-flag CFG lowering that routes
  exits through the loop header so the exit blocks stay on the cycle. That
  rewrites the emitted Rust for EVERY droppy loop and sits squarely in the
  cross-iteration loop-liveness area CLAUDE.md records as having miscompiled
  THREE times, with an explicit instruction not to retry it without a new
  idea and the byte-diff suite in the loop. Declining it was correct; the
  path back is recorded rather than attempted.
  **THE FENCE IS A SCALPEL, NOT A BAN ON `break` NEAR A DESTRUCTOR.** The
  analysis answers "does control always leave this loop?" in TWO conservative
  directions, because the two consumers need OPPOSITE errors: the
  OVER-approximation drives the rejection (being wrong gives a spurious
  reject), the UNDER-approximation drives the SKIP ("the body always leaves,
  so there is no back edge and nothing to relocate"). Using the
  over-approximation for both is what let `switch (i) { case 1: printf(..);
  return i; }` keep miscompiling in the first build -- measured, then fixed,
  then pinned.
  36 probes, every one byte-diffed against clang++. **13 shapes stay ACCEPTED
  and byte-identical**, including `continue`, a `break` with nothing
  observable, an effect BEFORE the decision, a `switch`-case `break`, an
  inner-loop `break`, a body that always leaves, and decls inside single- and
  two-exit relocated regions. Verified independently after landing: both hunt
  repros now take a located rejection, and `break`-with-no-effect still
  byte-matches (`body 0 / dtor 0 / body 1 / dtor 1 / after`).
  **TWO ADJACENT MISCOMPILES FOUND AND CLOSED IN THE SAME FAMILY**, neither
  in the brief:
   - `do { T a(i); } while (g(i) < n);` -- the do-while CONDITION is the
     `for` increment's twin and only the increment was gated. Native
     `body 0 / dtor 0 / cond 1` came out `body 0 / cond 1 / dtor 0`. Plain
     `while` is unaffected (measured) and stays accepted.
   - `for (i = 0; i < n; ++i, tick++)` -- the increment gate screened only for
     CALLS, so a global STORE walked through: `dtor 0 tick=1` versus native
     `dtor 0 tick=0`. Widened to the same observable-effect predicate.
  ONE EXISTING GOLDEN MOVED, forward not looser:
  `loop-escaping-place-opaque-reject.cpp` now hits the import-time fence
  instead of FR-152's pass-level one, because every read of an
  `emitrust.opaque` place is a call. Both refuse the same program; the new
  diagnostic fires a stage EARLIER and names the source DECLARATION plus a
  note at the offending effect, where the old one could only name the IR
  place. `CHECK-NOT: failed to legalize` is retained and FR-152's wording is
  still live, still pinned by its struct_def sibling
  (`loop-escaping-place-drop-reject.cpp`, whose escaping use `return r.id;`
  carries no effect for the new gate to catch).
  CAPABILITY COST, stated plainly: programs that previously imported and were
  SILENTLY WRONG now refuse. That is the sanctioned direction -- but it is a
  reduction, and the way back is the break-flag lowering above.
  Gate 997/997; clippy 101 -> 101 (+0); TRACTOR 40/252 (the gate sits under
  `userOrInheritedDestructor` and is unreachable from C); both ratchets
  unmoved. New needles tagged `cxx-drop-scope` in both the ledger and its
  `run_realworld.py` twin.
  NOT VERIFIED: the multi-exit SKIP is measured, not proved -- when the
  declaration itself sits in a region that always leaves the loop, the fence
  accepts it on the reasoning that the `let` and the drop relocate together,
  probed with a two-exit region and byte-identical, but that is one
  adversarial data point rather than a proof. `observableEffect` also treats
  reads as free, so a relocated VOLATILE read would slip through (volatile
  locals are rejected elsewhere, so no live case could be built).
