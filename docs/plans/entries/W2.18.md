- [x] W2.18 Single non-virtual inheritance: base as a first field.
  Spike verdict **GO-WITH-CONSTRAINTS** (2026-08-21; hand-written
  target image built with cargo and byte-diffed against
  `clang++ -std=c++17`, then a 216-line throwaway importer patch
  applied, measured and reverted). The image is `struct Derived {
  base: Base, y: i32 }` with inherited access flattened through the
  field -- `self.base.base_get()`, `self.base.x`,
  `self.base.base_new(a)`, and `self.base.base.base_get()` at three
  levels. It needs NO new dialect ops: the base-constructor call is
  literally the `emitrust.member ["base"]` + `emitrust.addr_of mut` +
  `func.call {emitrust.method_call}` shape the plain COMPOSITION probe
  already emits.
  AST measurements that shaped the traversal: an implicit inherited
  call (`get()` with no `this->`), an explicit `this->get()`, and an
  inherited field read or write are all ONE
  `ImplicitCastExpr <UncheckedDerivedToBase>` over `CXXThisExpr`;
  `Base::get()` adds a `NestedNameSpecifier` plus a `<NoOp>` above the
  cast, so the peel must skip `CK_NoOp`; and a two-hop chain is a
  SINGLE cast node carrying a TWO-ENTRY path, so `CastExpr::path()`
  must be walked rather than the cast counted.
  THE BLOCKER THE ANCHOR SHEET MISSED -- a measured SILENT MISCOMPILE,
  and the reason a naive version of this wave would have been strictly
  LESS safe than the composition it mimics.
  `ImportCStatements.cpp`'s `if (!init->isMemberInitializer()) continue;`
  silently drops the base's DEFAULT construction when the derived class
  declares no constructor of its own. Three byte-diffs through the real
  `--emit=crate --build`: native 9 / crate 2, native 10 / crate 1
  (NSDMI base), native 9 / crate 2. No diagnostic, no verifier, no type
  error -- just wrong numbers, where the composition equivalent already
  rejects with `constructor in value position`. Fixed on the spot by a
  base arm in `emitDefaultConstructInit`; all three then byte-identical.
  SECOND CHANNEL, also silent at the importer: a base class with a
  W2.17 destructor. `userDeclaredDestructor` keys on
  `hasUserDeclaredDestructor()`, which is FALSE for a merely-inheriting
  derived class, so the derived struct emitted
  `#[derive(Clone, Copy, Default)]` beside the base's `impl Drop` (rustc
  E0204) and `let _b: B;` that is never initialized and never dropped --
  and every W2.17 use-site gate (scope, by-value, array, global)
  silently failed to fire. Now `unsupported: base class with a
  destructor`.
  THE DESTRUCTOR-ORDER TEST THE WAVE WAS TOLD TO REJECT ON: it PASSES.
  Base-as-FIRST-field means the base drops before the other members,
  which is the reverse of C++ -- but a three-level `A <- B <- C` with
  printf destructors prints `~C / ~B / ~A` byte-identically, and the
  reason is structural rather than lucky: W2.17 already forbids every
  OTHER droppy member, so there is never a second droppy field whose
  order could be observed. Recorded as a standing dependency, not a
  coincidence.
  UPCASTS AND SLICING all stay LOCATED rejections, each measured:
  `takesBase(d)` by value (C++ object slicing) dies at
  `unsupported cast (DerivedToBase)` BEFORE any whole-object move,
  because the trivial-copy unwrap calls `emitRValue` on the cast
  itself; `takesBase(&d)` gives `unsupported pointer cast
  (DerivedToBase)`; `Base *p = &d;` is blocked by pre-existing pointer
  machinery; `Base &r = d;` by the reference rejection. A mis-borrowed
  receiver is caught by the `emitrust.addr_of` verifier (pointee
  `!emitrust.struct<"Base">` vs value `!emitrust.struct<"Derived">`) --
  struct types always differ by name, so it always fires; it is a hard
  located failure but NOT an `unsupported:` wording, so it can never
  reach the rejection ledger.
  A SIMPLIFICATION the measurements bought: with the admission guard
  `numBases() == 1 && !isVirtual() && AS_public`, multiple inheritance,
  virtual inheritance and private/protected inheritance ALL keep hitting
  the existing `base classes are not supported` wording -- no new
  spellings needed. An undefined base needs none either: clang
  hard-errors `base class has incomplete type` first.
  EMPTY BASE: `struct A {}; struct B : A { int y; };` was emitting a
  spurious `base: [u8; 1]` filler field (unobservable, since clang folds
  `sizeof` at import, but divergent from C++ empty-base optimization).
  The base is now skipped -- which in turn means an inherited call or a
  base constructor BODY through it has no field to project, so both got
  their own located rejections rather than rustc E0609 or a silently
  dropped constructor body.
  THE STALE-SCREEN FINDING, worth more than the feature: the FR-40
  coloring probe (`lib/Project/ItemColoring.cpp`) is
  importer-INDEPENDENT, and its test did not fail under the spike patch

  Four new wordings, three tags (`cxx-drop-base`,
  `cxx-inheritance-empty-base`, `cxx-inheritance-upcast`), mirrored into

  shadowing (`A::v` vs `B::v`), a W2.16 class template as the DERIVED
  class, and the `appendField` duplicate-name guard firing for
  `struct B : A { int base; }` -- which works only because the base
  field is pushed FIRST.
  Gates: full meson suite 712/712 (fast 509 + slow/EndToEnd 203), 0
