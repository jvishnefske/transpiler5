- [x] FR-75 Requirement-trait pointer params are REGION-typed (slices),
  not single-element refs (fidelity defect found 2026-08-14 while
  chasing the solo-TU tinycrypt stubs). Today a declaration-only
  `extern void helper(unsigned char *buf, unsigned len)` lands in the
  FR-52 `Externals` trait as `fn helper(v0: &mut u8, v1: u32)` and the
  call site passes `&mut b[0]` — ONE byte. A C pointer parameter
  denotes a REGION; an implementor of the trait cannot faithfully
  implement any helper that touches `buf[1..]`, so the requirement
  signature misrepresents the contract the C program actually has.
  This is a deliberate ABI change to the young FR-52 trait surface
  (extern-plugin corpus + lib-crate goldens shift, updated in the same
  change): a scalar-pointer parameter in a requirement signature maps
  to `&mut [T]` / `&[T]` (constness from the pointee qualifier), and
  every call site lowers its argument as a REGION view — a top-level
  array, an FR-74 member array, or a re-sliced slice param, at the
  argument's cursor. A call site whose argument cannot produce a
  region view keeps a located rejection (never a silent one-element
  borrow). Declaration-only `void *` params join by CALL-SITE
  CONSENSUS: they map to `&mut [u8]`/`&[u8]` iff every call site in
  the TU passes an admissible byte view (the solo-TU `_set`/`_copy`
  shape — the definition-body scan of FR-71 cannot run without a
  body); any non-byte or non-region call site keeps the verbatim
  void-param rejection. isExternalRequirementShape grows accordingly;
  the FR-57a defer path is untouched (its obligations are link-step,
  not trait). Gates: existing trait pins (trait-def.mlir,
  multi-tu-external-requirement*.c, lib-crate-externals-trait.c and
  the FR-70 global twin, Project/externals-trait.c, extern-plugin
  RealWorld scores) updated IN THE SAME CHANGE with the slice
  signatures — any score movement must be improvement-only; new pins
  for the void* consensus admission and its frontier (mixed call
  sites reject); EndToEnd lib-crate test's consumer impl implements a
  multi-byte-writing helper THROUGH the slice — the shape the old ABI
  could not express — and byte-diffs against a clang native given the
  same helper; full lit 100%.
  **SPIKE VERDICT: GO (2026-08-14).** The whole feature is a
  CLASSIFICATION change: body-less pointer params were ParamKind::
  ScalarRef by explicit fallthrough (no "Phase-1b slice fallback"
  exists — the FR-74-spike recollection was wrong), and the Slice
  branch + emitBorrowArgument's type-driven paths already produce
  every call-site form. Hand IR (slice-typed requirement items, const
  and mut) passes the lower-external-requirements pass VERBATIM (it is
  type-transparent), renders `fn helper(v0: &mut [u8], v1: u32)` with
  `&mut b[cursor..]` call sites, and a two-line-spliced lib crate with
  a consumer writing EVERY byte through the slice byte-diffed the
  clang native. Measured decisions: eager classification restricted to
  ARITHMETIC pointees; cross-TU decl-first+slice-body-def ordering
  IMPROVES (the refinement mismatch rejection becomes type-equal)
  while decl-first+scalar-body-def flips to the located conflicting-
  redeclaration rejection; the previously-ACCEPTED trait shape
  `helper(&x, 1)` (address of a scalar) deliberately flips to the
  located address-of-scalar rejection — fidelity over coverage,

  requirements are int-only). void* consensus rides the existing

  emitrust-import-c never applies --externals-trait (importC ignores
