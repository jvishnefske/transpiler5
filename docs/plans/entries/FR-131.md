- [x] FR-131 DEFECT (found by FR-61f-8's spike, pre-existing, SEPARATE
  channel; FIXED 2026-08-28): `printf("")` with an EMPTY format string and
  no arguments emitted `print!()`, which is not valid Rust -- rustc rejects
  it with "requires at least a format string argument" and the crate fails
  to build. Minimal repro is two lines:
      int printf(const char *, ...);
      int main(void) { printf(""); return 0; }
  Exit-0 unbuildable, which is the SAFE direction (a hard rustc error, never
  a miscompile) but still the rejection-is-a-feature policy violated. Found
  while writing FR-61f-8's test, where a body needed a call that did nothing
  observable; nothing in either corpus calls `printf` with an empty format,
  which is why no ledger saw it.
  ROOT CAUSE: `emitPrintMacro`'s bare-macro shortcut fired on EMPTINESS when
  its real precondition is THE NEWLINE FOLD. The shortcut is correct for the
  `ln` variants -- `printf("\n")` pops its newline, leaves an empty format,
  and `println!()` is both valid and what avoids
  clippy::println_empty_string. A format that was ALREADY empty never folded,
  so the macro is still `print!`, and `print!()` is not valid Rust. Fixed by
  gating the shortcut on a `foldedNewline` flag; an unfolded empty format
  falls through and keeps its zero-length literal.
  `print!("")` compiles clean and writes ZERO BYTES, byte-identical to what
  C's `printf("")` does, so this is behaviour-preserving rather than a
  workaround. CLIPPY MEASURED, not assumed, on the actual emitted crate:
  zero warnings under `clippy::all`, and none on `print!("")` even under
  `+pedantic`. A control probe confirmed the lint set was live (`print!("x\n")`
  did fire print_with_newline). There is a `clippy::println_empty_string` but
  NO non-`ln` analogue, so the ratchet is untouched.
  THE STDERR TWIN IS UNREACHABLE, and the spec's demand for `eprint!("")` was
  wrong: measured, C has no accepted route to the stderr twins at all
  (`fprintf(stderr, "")` is a located rejection -- "fprintf to a FILE* stream
  (only the devirtualized stdout form is supported)"), and the W2.22
  `std::cerr` path early-returns on an empty chain, so `std::cerr << ""`
  correctly emits NO CALL and only the `std::endl` fold (an `ln` variant)
  reaches `emitPrintMacro`. The gate is still symmetric -- one shared
  `foldedNewline` bool, not a string compare on the macro name -- and both
  facts are pinned instead.
  Pinned by test/Import/C/printf-empty-format.c (which also carries the
  BYTE-IDENTITY guard that `printf("\n")` still emits the bare `println!()`,
  the case the shortcut exists to serve and the one a too-broad gate would
  break), printf-empty-format-invalid.c, test/Import/Cpp/ostream-empty-format.cpp,
  and the real oracle test/EndToEnd/printf-empty-format.c -- which pre-fix
  failed with 8x "requires at least a format string argument" before any
  diff could run, i.e. the crate did not compile at all.
